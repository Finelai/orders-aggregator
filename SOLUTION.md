# Решение: статистика заказов

## Что сделано

Дневная статистика учитывает только заказы со статусом `paid`. Поле `gross` содержит сумму до скидки, `net` — сумму оплаты, `discount` — разницу между ними. Поле `total` сохраняет прежний смысл и равно `gross`. Дни без оплаченных заказов содержат нули.

Сервис получает `amountPaid` из синхронизации и вебхуков. Данные хранятся в копейках. При повторной доставке применяется более новая версия заказа. Если у сохранённой версии оплаченная сумма неизвестна, её можно заполнить из события с тем же `updatedAt`. Обновление версии выполняется атомарно в базе.

## Причина расхождения по дням

Сервис применял текущее смещение часового пояса ко всем заказам. Для `c_7` внешний API вернул `Europe/Berlin`: 29 марта 2026 года смещение изменилось с UTC+1 на UTC+2. Поэтому при расчёте с зимним смещением заказы, созданные вскоре после полуночи по летнему времени, попадали в предыдущий день. Время запуска запроса влияло на результат.

На отдельной базе выполнены синхронизация и доставка вебхуков. До исправления ответ за 27–31 марта сравнен с группировкой оплаченных заказов в PostgreSQL по `created_at AT TIME ZONE 'Europe/Berlin'`. Обнаружены четыре заказа с неверной датой: один смещался с 30 на 29 марта, один — с 31 на 30 марта, ещё два — с 1 апреля на 31 марта. После исправления повторный ответ на тех же данных совпал с независимой группировкой по всем дням и денежным полям до копейки.

Теперь календарная дата определяется для каждого заказа по времени его создания и часовому поясу клиента через `Intl.DateTimeFormat`. Запас при выборке и фильтрация по запрошенным датам сохранены. Отчёт платёжной системы для прямого сравнения недоступен.

## Допущения и ограничения

- Если `amountPaid` отсутствует, оплата принимается равной `amount`. Это может скрыть скидку, если она была, но API не передал сумму оплаты.
- Миграция оставляет сумму оплаты старых записей неизвестной. При чтении применяется то же допущение; повторная синхронизация может восстановить сумму, если API её вернёт для той же версии.
- `discountPercent` не используется: сумма оплаты берётся из `amountPaid`, а скидка вычисляется как разница сумм.
- Доли копейки отбрасываются. Сумма в статистике при этом может быть меньше исходной на долю копейки.
- Значение `amountPaid` больше `amount` не запрещено контрактом. В таком случае скидка получается отрицательной.
- При проверке всех 5030 заказов mock API оба поля скидки отсутствовали в 1177 записях. Это наблюдение относится к проверенному набору данных.

## Проверка

Выполнены `npm run lint`, `npm run format:check` и `npm run typecheck`. На отдельной временной базе PostgreSQL запущены 45 автоматических тестов; все прошли. Проверены скидки, денежные суммы, статусы, вебхуки, синхронизация и восстановление старых записей после миграции. Дополнительно проверены весенний и осенний переходы времени, разные даты запроса и часовые пояса процесса, отрицательное и дробное смещения, UTC−12 и UTC+14, границы периода и пустые дни.

Вручную проверены синхронизация, доставка вебхуков и ответ статистики. Для `result.json` запущен отдельный Compose-проект с чистой базой на основе `docker-compose.yml`. Чтобы не занимать порты действующего стенда, приложение добавлено в сеть Compose, а портам PostgreSQL и mock API отключена публикация. После запуска базы и приложения запрос `POST /sync` обработал 5030 заказов на 52 страницах; затем команда доставки вебхуков отправила 92 события и получила 92 ответа 200. В команде из README адрес назначения изменён на `http://app:3000/webhooks/order`, доступный внутри сети Compose. После этого запрошена статистика `c_7` за 27–31 марта и сохранена в `result.json`. Её суммы вручную сверены с группировкой заказов в PostgreSQL по локальным датам и совпали до копейки.

## Что можно доделать

Сверить итог с отчётом платёжной системы, когда он будет доступен. Уточнить контракт на случай отсутствующего `amountPaid` и дробей копейки, чтобы не полагаться на указанные выше допущения.
